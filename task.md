# Требования

## Аккаунт
- Регистрация и вход по email и паролю. Выход из аккаунта.
- После перезагрузки страницы сессия сохраняется. После выхода и повторного входа данные на месте.
- Неавторизованный пользователь видит только экран входа/регистрации. Прямой переход на внутренние страницы ведёт на вход.

## Заявка
Поля (все обязательные): название, описание задачи, категория.
- Категория: «Бот», «Интеграция», «Отчёт», «Другое».
- Статус: «Новая», «В работе», «Завершена». У новой заявки статус «Новая» ставится автоматически (default в БД, а не только в UI).
- Дата создания ставится автоматически (created_at), ещё поле updated_at, обновляется триггером.

## Работа с заявками
- Список: название, категория, дата создания, статус.
- Открыть заявку, отредактировать название, описание, категорию.
- Пользователь сам меняет статус своей заявки (быстро, прямо из списка или из карточки).
- Поиск по названию (без учёта регистра, с debounce ~300 мс) и фильтр по статусу («Все», «Новая», «В работе», «Завершена»). Работают вместе. Поиск и фильтр можно делать запросом к Supabase (ilike + eq) или на клиенте, выбери и опиши в README.
- Сортировка по умолчанию: новые сверху.

## Безопасность (самое важное)
- Таблица tickets: id (uuid, pk, default gen_random_uuid()), user_id (uuid, not null, default auth.uid(), references auth.users on delete cascade), title, description, category, status, created_at, updated_at.
- CHECK-ограничения в БД: category и status только из допустимых значений. title и description не пустые (после trim), разумные лимиты длины (например title ≤ 200, description ≤ 5000).
- RLS включён. Политики для роли authenticated: SELECT/INSERT/UPDATE/DELETE только где user_id = (select auth.uid()). WITH CHECK на INSERT/UPDATE тоже по user_id, чтобы нельзя было создать или переписать заявку на чужой user_id. Для anon доступа нет.
- Запрет менять user_id и created_at при UPDATE (триггер или column privileges).
- Индексы: по (user_id, created_at desc) и, при желании, по (user_id, status).
- Всё это оформи как SQL-миграцию в репозитории: supabase/migrations/0001_init.sql. Она должна запускаться на чистом проекте целиком, без ручных правок.

## Интерфейс
Язык интерфейса — русский. Стиль — чистый, минималистичный, светлый (тёмную тему можно как бонус, не в ущерб остальному).

Экран входа/регистрации:
- Одна карточка по центру, переключатель «Вход / Регистрация», поля Email и Пароль, кнопка отправки, у пароля кнопка «показать».
- Валидация: корректный email, пароль ≥ 6 символов (под настройки Supabase), понятные сообщения под полями.

Основной экран (после входа):
- Шапка: название приложения, email пользователя, кнопка «Выйти».
- Панель управления: поле поиска, фильтр статуса (select или сегменты), кнопка «Новая заявка».
- Список заявок: на десктопе таблица или карточки в строку (название, категория-бейдж, дата, статус-бейдж/селект). На телефоне (узкий экран ≥ 320 px) — карточки в одну колонку, без горизонтального скролла, крупные зоны нажатия (≥ 44 px).
- Создание/редактирование: модальное окно (на мобильном — во весь экран) или отдельная страница. Поля: название (input), описание (textarea), категория (select), для существующей заявки ещё статус. Кнопки «Сохранить» и «Отмена».
- Статус можно менять быстро прямо из списка (select/меню). Изменение сразу сохраняется, показывается индикатор и результат.

Состояния:
- Загрузка (скелетоны или спиннер), пустой список («У вас пока нет заявок» + кнопка создать), пустой результат поиска/фильтра («Ничего не найдено» + сброс фильтров).
- Успех: тост «Заявка создана» / «Изменения сохранены» / «Статус обновлён».
- Ошибка: понятный тост или inline-сообщение на русском («Не удалось сохранить. Проверьте соединение и попробуйте ещё раз»). Данные, введённые в форму, при ошибке НЕ теряются.

## Защита от двойного нажатия
- Пока идёт сохранение: кнопка «Сохранить» disabled и показывает спиннер, форма заблокирована.
- Дополнительно защита на уровне кода (ref/флаг isSubmitting, проверка в обработчике), чтобы двойной клик или Enter, нажатый дважды, не отправили два запроса.
- Для создания добавь идемпотентность: id заявки генерируется на клиенте (crypto.randomUUID()) один раз на открытие формы и передаётся в insert. Повторная отправка с тем же id не создаст дубликат (обработай конфликт уникальности как «уже сохранено»).
- То же для смены статуса и редактирования: пока идёт запрос, контрол блокируется.

# Edge cases, которые нужно учесть и проверить

Аккаунт:
- Регистрация с уже существующим email. Понятное сообщение, а не «User already registered» в сыром виде.
- Неверный пароль/email при входе: «Неверный email или пароль».
- Подтверждение почты: для тестового отключи Confirm email в настройках Supabase и опиши это в README. Если включено, при регистрации покажи сообщение «Проверьте почту». Приложение должно корректно работать в обоих режимах.
- Истёкшая сессия/токен: при ошибке 401/JWT expired перекинуть на вход с сообщением, не оставлять сломанный экран.
- Двойной клик по «Войти/Зарегистрироваться» не отправляет два запроса.
- Выход очищает локальное состояние, следующий пользователь в той же вкладке не видит чужих данных (сбрось кеш/стейт).

Данные:
- Пустые или состоящие из пробелов название/описание: ошибка валидации на клиенте и CHECK в БД.
- Слишком длинные значения: счётчик символов или ограничение maxLength.
- Подозрительные символы (HTML, эмодзи, кавычки): отображаются как текст, без XSS (никакого dangerouslySetInnerHTML).
- Поиск: спецсимволы % и _ экранируй, чтобы они искались как обычные символы. Пустой поиск = без фильтра. Лишние пробелы по краям обрезаются.
- Быстрый ввод в поиске: отмена/игнор устаревших ответов (race condition), чтобы старый ответ не затёр новый.
- Редактирование заявки, удалённой или недоступной (например, открыта в двух вкладках): понятное сообщение «Заявка не найдена» и возврат к списку.
- Потеря сети при сохранении: ошибка, данные формы сохранены, можно повторить.
- Большое число заявок: пагинация или «Загрузить ещё» (по 20–50), чтобы не грузить всё сразу.
- Даты показываются в локальном часовом поясе пользователя в формате ДД.ММ.ГГГГ ЧЧ:ММ.

Доступ:
- Прямой запрос к REST API Supabase (curl с anon key и JWT пользователя B) к заявке пользователя A возвращает пустой результат/ошибку, а UPDATE/DELETE чужой строки затрагивает 0 строк.
- INSERT с чужим user_id отклоняется RLS.
- Запрос без JWT (только anon key) не возвращает заявки.
- Попытка изменить user_id собственной заявки отклоняется.

Интерфейс:
- Ширина 320, 375, 768, 1280 px: нет горизонтального скролла, ничего не обрезается, модалка помещается в экран, клавиатура на телефоне не перекрывает кнопку «Сохранить».
- Навигация с клавиатуры: Tab, Enter, Esc закрывает модалку. У контролов есть label и фокус-стили.
- Контраст текста и бейджей достаточный.

# Исходное ТЗ

Задача 3. Веб-приложение с AI и Supabase. Нужен небольшой веб-сервис для сотрудников компании, чтобы оставлять заявки на автоматизацию и следить за их состоянием. Пользователь может зарегистрироваться, добавить заявку и вернуться к ней позже. Для авторизации и хранения данных используется Supabase.

Аккаунт: регистрация и вход по email и паролю; выход.
Заявка: название, описание задачи, категория («Бот», «Интеграция», «Отчёт», «Другое»), все поля обязательны; новая заявка автоматически получает статус «Новая».
Работа с заявками: в списке видны название, категория, дата создания, статус; пользователь может открыть и отредактировать свою заявку; пользователь сам меняет статус («Новая», «В работе», «Завершена»); есть поиск по названию и фильтр по статусу.
Результат: данные сохраняются в Supabase и доступны после обновления страницы и повторного входа; каждый пользователь видит и изменяет только свои заявки (ограничение действует на уровне данных, не только в интерфейсе); удобно на компьютере и телефоне; после сохранения виден результат, при ошибке понятное сообщение; пока идёт сохранение, повторное нажатие не создаёт дубликаты.
На что обратят внимание: понятная логика; корректная работа с данными; доступ к заявкам (в том числе при обращении к данным напрямую); ошибки и сохранение; защита от дубликатов; удобство интерфейса на компьютере и узком экране; подход к использованию AI.
Как сдавать: ссылка на работающее приложение; ссылка на Git-репозиторий без секретных ключей; описание настройки Supabase для повторного запуска; короткое описание AI-инструментов (что получилось сразу, какие проблемы возникли, как исправлены); список известных недоработок. Проверить, что ссылки открываются и материалы доступны.
